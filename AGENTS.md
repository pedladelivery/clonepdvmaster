# Agent rules

- Inserts into `sales`, `stock_movements` and `transactions` must set `store_id` via `requireStoreId()` (src/lib/currentStore.ts) — the column is NOT NULL and RLS scopes by store.
- Product add-ons live in `complement_groups` / `complement_items` / `product_complement_groups`; a sale item's chosen add-ons are stored as text lines in `sale_items.notes` ("Grupo: Nx Item", "Obs: ...") via `encodeItemNotes`/`decodeItemNotes` — the database is shared with another app that uses this format.
- Storage buckets are private (workspace blocks public buckets); uploads return long-lived signed URLs via `uploadedFileUrl`.
- Users created through `create-admin-user` get `profiles.store_id` and a `user_stores` row, otherwise store-scoped RLS hides all sales from them.
- Painel Master locks (`pdv_controls`: admin/tables/sales) are enforced by DB triggers for anon/authenticated callers and raise `PDV_BLOCKED:<key>:<msg>`; service-role code must check `pdv_controls` itself. UI reads them via `PdvControlsProvider` — new admin screens or sale-writing flows must respect both.
- The /master area uses its own login (`master-auth`/`master-admin` edge functions, `x-master-session` header, hashed sessions); its tables are service-role only. Master API calls must follow the approved contract only — no invented endpoints or JSON.
- All Painel Master HTTP calls go through `masterRequest`/`loadCredentials` in supabase/functions/_shared/master.ts (token decrypted server-side, responses passed through `sanitize`); the frontend never calls the Master directly. `pdv-subscription` serves Minha Assinatura and checks owner/`subscription` permission server-side.
- Master sync (heartbeat, pending commands, ACK, result, reports) lives in supabase/functions/_shared/sync.ts `runSync`; `master-sync` (pg_cron every minute) and master-admin `sync_now` both call it. It self-throttles by `sync_interval_seconds`, takes `master_try_sync_lock`, and dedupes by `master_commands.command_id` so a command executes once and only its stored result is resent.
- The Master sync cadence and log retention are owner-chosen in /master → Integração and saved only via `master_save_sync_settings` (updates `sync_interval_seconds` and reschedules the `pdv-master-sync` cron job); Master heartbeat replies never override them. `pdv-master-cleanup` runs `master_cleanup_logs` daily — why: keep cron run history and heartbeat events from growing unbounded.
- /master tabs Relatórios, Minha Assinatura and Sistema reuse the PDV components; while /master is open they run through `@/lib/dbClient` (a proxy over the PDV client) switched by `MasterPdvAccess` to a memory-only session of the first admin, minted by master-admin `pdv_bridge` — why: Master login gets these screens without touching the PDV's own browser login or credentials. Code used by those screens must import `supabase` from `@/lib/dbClient`. `SystemTab` is a copy of Configurações → Sistema — keep both in step.
- Minha Assinatura reads `/subscription`, `/charges` and `/payments` independently in `pdv-subscription` (rules in its `finance.ts`): only the Master code `endpoint_not_found` means "not published" and pauses that one service; checkout is always created by the Master via `POST /charges/{id}/checkout` and the PDV only opens the returned `checkout_url` — why: a missing service or empty list must never hide the others, and payment confirmation belongs to the Master webhook. `master_integration.financial_unpublished_until` is no longer used.
- Any new tab or print window that needs data loaded first is opened during the click (`prepareTab`/`openPreparedTab` in src/lib/checkoutWindow.ts, or `window.open` before the first await) and `opener` is cut only after navigation starts — why: browsers block tabs opened after a wait, and inside the embedded preview a tab without opener cannot be navigated and stays blank.
- Whether a charge shows a payment option is decided only by `canPayCharge`, and whether it sits in Cobranças atuais or Histórico de cobranças only by `splitCharges`, both in src/lib/subscriptionView.ts from the Master's status (unknown statuses stay current); tests in tests/subscriptionView.test.ts run with `deno test tests/` — why: a confirmed charge must never be paid twice and no record may be hidden.
- License suspension: `master_integration.license_status` (set only by the Master sync — `license.*` commands or explicit heartbeat indicators parsed by `licenseFromMaster` in supabase/functions/_shared/license.ts) is the source of truth; `pdv_0_license_lock` statement triggers on every public table except `master_*`, `pdv_controls`, `pdv_license_state` refuse anon/authenticated writes with SQLSTATE 42501 (HTTP 403), service-role functions call `isLicenseSuspended` themselves, and the UI reads the mirror `pdv_license_state` via `LicenseProvider` — why: suspension must hold server-side, never touch `pdv_controls`, and leave Minha Assinatura and the Master sync working. New tables need the same trigger.

- Installation management (/master → Integração): master-admin `export_backup`/`import_backup`/`prepare_new_installation`/`bind_installation` with backup format and reset fields in supabase/functions/_shared/installation.ts; backups keep the token encrypted and are HMAC-bound to `MASTER_ENCRYPTION_KEY`, prepare keeps `license_status`, `master_users`, `pdv_controls` and all operational tables — why: reuse the code for new stores without leaking or unlocking the old identity.
